================================================================

This is the single practical runbook consolidating the original Steps 1–9C
plus the later 9D, 9E, Step 10 and Step 11 work.

RULES
-----
• Preserve existing functionality.
• Do not delete a source file because its filename says Step, Fixed, Updated,
  Backup, Final, Complete, Old, etc. Compare functionality first.

• MAX_QUERY_ROWS=0 means dynamic/no artificial report-row ceiling.
• Preview/visualization remain browser-bounded.

APPENDIX A — IMPLEMENTATION HISTORY / SOURCE-PRESERVATION RULE
================================================================

The original development process used separate STEP README files because each
phase was implemented and tested independently. This master document is the
operational consolidation of that work.

The following implementation boundaries are intentional and must be retained:

STEP 2A
-------
security.py establishes Fernet encryption/decryption and deliberately does not
modify the connection registry. Existing plaintext credentials remain untouched
until the controlled Step 2B migration.

STEP 2B
-------
connection_registry.py integrates encryption and safely migrates existing saved
credentials. list/create/update responses must not expose passwords, while
runtime lookup may decrypt the credential in memory.

STEP 3A
-------
auth.py establishes password hashing and signed token support without changing
existing API routes or frontend behavior.

STEP 3B
-------
user_registry.py introduces the local users registry and supports admin and
report_user roles. Stored passwords are hashes, never plaintext.

STEP 3C
-------
auth_api.py introduces login, current-user and logout endpoints. main.py is
updated only to mount the authentication router.

STEP 3D
-------
Authentication is then applied to existing protected APIs. This is separate
from the fine-grained authorization introduced in Step 4.

STEP 4
------
permissions.py provides fine-grained authorization. Frontend visibility is
not considered sufficient security; the backend must enforce the permission.

STEP 5A
-------
connection_access.py adds connection-level access control without changing the
underlying database credentials model.

STEP 6 / 6B
-----------
MAX_QUERY_ROWS=0 removes an artificial application row ceiling, but request
size, timeout, JOIN count, memory, export size and concurrency protections
remain independent.

STEP 7
------
Logging is deliberately separated into application and audit logs. Secrets,
tokens and request bodies must not be logged.

STEP 8 / 8B / 8C
----------------
Application-state backups are separate from database-content backups.
Recovery-test is deliberately non-destructive. External backup storage is
provider-neutral because the eventual deployment is server-based.

STEP 9
------
Large-data behavior is designed around pushdown, projection, streaming,
server-side processing and bounded browser rendering.

STEP 9B
-------
query_pushdown.py and streaming.py establish a structured planner and streaming
foundation without replacing connector-specific execution.

STEP 9C
-------
MySQL receives actual connector-specific filter pushdown, projection and
streaming. Cross-source JOIN semantics remain under the existing JOIN engine.

STEP 9D
-------
MongoDB receives actual aggregation pipeline pushdown:
$match, $project, safe $sort/$limit, aggregation cursor batching and
allowDiskUse. Complex OR/calculated expressions are not blindly pushed down.

STEP 9D FIX
-----------
The MongoDB execution path must use the existing create_mongo_connection()
helper rather than introducing an undefined create_mongodb_client() path.

STEP 9E
-------
Same-source JOINs are candidates for source-local optimization; cross-source
JOINs continue through the existing semantic JOIN engine.

STEP 9E / STEP 10 FIXES
-----------------------
The optimized JOIN path must preserve requested report columns and aliases.
Background jobs must pass the complete report-query payload to the existing
executor, including datasets, joins, columns, filters, sorts, group_by,
aggregations, calculated_columns and limit.

MONGODB FIELD QUALIFICATION FIX
-------------------------------
MongoDB returned fields must be qualified with the dataset ID so that the
existing JOIN/report layer can distinguish fields from different datasets.
The previously observed undefined local rows variable must not be reintroduced.

STEP 10
-------
Background execution adds queueing, status, cancellation and resource
management. A completed job is not cancellable; cancellation applies only
while the job is in a cancellable state.

STEP 11
-------
Production security and frontend integration add environment-configurable
frontend API addressing, permission helpers, production security checks and
server-oriented configuration while preserving the existing reporting,
JOIN, pushdown, backup and execution behavior.

BACKGROUND JOB
--------------
POST /execution/jobs should return:
    success = true
    job_id = <id>
    status = queued

GET /execution/jobs/{job_id} should eventually show:
    completed
or
    failed
or
    cancelled

A completed job must not be cancellable. The response:
    "Job cannot be cancelled in its current state."
is correct for an already completed job.

If a job fails with:
    _execute_report_query_unbounded() missing ... joins, columns, filters,
    sorts, group_by, aggregations, calculated_columns, limit

then the background payload normalization is incomplete and Step 9E/Step 10
job-payload integration must be checked.

MANAGE USERS
------------
Admin must be able to access Manage Users through the frontend and backend
permissions must independently enforce authorization.

A missing frontend Manage Users entry is an integration issue, not a reason
to remove the backend user-management functionality.


================================================================
APPENDIX C — PRODUCTION SERVER PRINCIPLES
================================================================

The local Windows environment is a development/test environment.

The future production deployment is expected to run on a server.

Therefore:

1. Paths must not depend on a developer's Windows username.
2. Configuration must come from environment/server configuration.
3. Database credentials must not be hard-coded.
4. Encryption keys must be persistent across restarts/deployments.
5. Backup storage should support an external/off-machine target.
6. Production database backup is separate from application-state backup.
7. Browser rendering must remain bounded even when reports contain millions
   of rows.
8. Server-side filtering/aggregation/pushdown should be preferred.
9. Streaming should prevent unnecessary full-result buffering.
10. Resource controls must remain enabled even though MAX_QUERY_ROWS=0.
11. Horizontal scaling requires shared infrastructure for state that is
    currently process-local.
12. Reverse proxy/TLS/security headers/CORS must be configured according to
    the real deployment topology.

MULTI-INSTANCE WARNING
----------------------
The current background job manager is process-local. It is suitable for the
current controlled deployment/testing architecture but must not be assumed to
be a distributed job queue.

Before running multiple backend workers/instances, introduce a shared job
queue/worker architecture such as Redis + Celery/RQ or an equivalent design,
and review session/token-revocation state for shared access.

DATABASE WARNING
----------------
The sample MySQL and MongoDB databases used during development are not
application backup contents.

A production backup plan must separately cover:
    MySQL
    MongoDB
    any future ClickHouse/other production sources

The application-state backup protects application configuration/state, not
the millions of rows stored in external database systems.


================================================================
APPENDIX D — SAFE CLEANUP POLICY
================================================================

"Cleanup" means:

    • remove dead imports after verification
    • remove unreachable code after verification
    • normalize formatting
    • remove duplicated CSS rules after visual/build verification
    • consolidate genuinely duplicated helpers
    • standardize environment/config handling
    • improve naming where references are updated consistently
    • remove generated development artifacts from deployment packages

"Cleanup" does NOT mean:

    • delete Step files
    • delete Fixed files
    • delete Updated files
    • delete Backup files
    • delete Final files
    • delete Complete files
    • delete alternative JSX/Python implementations
    • replace a component merely because another version has a newer filename

Before removing any source file:

    1. Search every import/reference.
    2. Compare its functionality with the proposed replacement.
    3. Identify unique functions/routes/UI behavior.
    4. Merge unique functionality if appropriate.
    5. Compile backend.
    6. Build frontend.
    7. Run regression tests.
    8. Create rollback backup.
    9. Only then remove the file if it is proven redundant.

The filename is never sufficient evidence of redundancy.
